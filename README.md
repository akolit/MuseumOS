## Who this is for

MuseumOS is built for **small museums and archives with large collections and
small teams** — the situation where off-the-shelf collection-management software
is either far too heavy or far too expensive, and the collection is currently
living in a pile of spreadsheets.

It is designed around how such a team actually works: a couple of curators
adding and validating records at a desk, and volunteers standing in front of a
shelf with a phone, photographing what's on it.

It was written for a vintage-computing collection, so the default categories
lean that way — but nothing about the design is specific to computers. If you
catalogue objects that fall into groups, and each group needs its own fields,
the model fits. See [adapting it](#adapting-it-to-your-collection).

**It might not be for you if** you need loans and exhibition management,
integration with a national aggregator, or a public-facing catalogue website —
MuseumOS is an internal tool, and stops at the museum's own door.

## Quick start

You need **Node.js 22+**, **pnpm 10+** (`corepack enable`) and **Docker**.

```bash
git clone <your-fork-url> museumos && cd museumos
pnpm install
cp .env.example .env
docker compose up -d postgres
pnpm db:generate && pnpm db:migrate && pnpm db:seed
pnpm dev
```

The seed prints a generated admin password **once** — save it:

```
  Admin user:
    ✓ Created admin: admin@museumos.local (role: admin)
    ⚠ Generated password (shown once — save it now): kJ8x...
```

| Service | URL |
|---------|-----|
| Web admin | http://localhost:5173 |
| API | http://localhost:3000/api |
| Capture PWA | http://localhost:5174 (`pnpm dev:pwa`) |

PostgreSQL is the only service the app needs. To pick your own admin password
instead of a generated one, set `SEED_ADMIN_PASSWORD` before seeding.

Ready to go live? See **[DEPLOY.md](DEPLOY.md)**.

## What you get

**Cataloguing**
- One flexible `exhibits` table: typed core columns plus a JSONB `attributes`
  column, so every category carries its own fields — *Processor / RAM / OS* for
  computers, *Author / Publisher / Language* for books — without a migration
  each time you add one.
- Per-category forms driven by JSON Schema, including dropdowns and type-ahead
  pickers that keep values consistent without locking out new ones.
- Soft-delete and restore, a validate/publish workflow, bulk edits, CSV/JSON export.

**Search**
- Accent-insensitive, Greek-aware full-text search (`unaccent` + `pg_trgm`,
  `simple` config, no stemming) — so `κλειδαριθμοσ` finds *Κλειδάριθμος*.
- Leading-zero-insensitive ID matching: `bk4` finds `BK00004`.
- Sortable, filterable columns and per-category type filters.

**Media**
- Upload from desktop or phone. Originals on disk, with 320 / 640 / 1024 WebP
  thumbnails pre-generated by `sharp`.
- In-place rotation with cache busting, broken-image fallbacks, hover previews,
  and human-readable filenames (`PC00544_1.jpg`).

**Donors**
- Donor profiles (contact, address, tax ID, first-donation date, legacy registry
  IDs) with a searchable picker and an opt-in public donor list.
- Attach scanned donation forms as PDF or image; PDFs get a rendered first-page
  preview.

**Mobile capture**
- Installable, offline-capable PWA: scan a QR code, compress photos on-device,
  fix details on the spot. List, small-grid and large-grid views.

**Curation & collaboration**
- Per-exhibit conservation log (dated events and notes), an audit log on every
  mutation, a floor-plan editor, and QR label printing.
- Roles (`viewer`, `curator`, `senior_curator`, `admin`) with an editable
  per-resource permission matrix.

**Optional integrations** — comparable listings via the eBay Browse API,
Wikidata enrichment, and a social-marketing composer (Meta OAuth). All off
unless configured.

See [CHANGELOG.md](CHANGELOG.md) for the dated feature history.

## How it works

```
            ┌─────────────┐         ┌─────────────┐
            │  Web admin  │         │ Capture PWA │
            │ React+Vite  │         │ React+Vite  │
            └──────┬──────┘         └──────┬──────┘
                   │   /api (session cookies)
                   └───────────┬───────────┘
                          ┌────▼────┐
                          │   API   │  NestJS
                          │ (Prisma)│  RBAC · audit · sharp
                          └────┬────┘
                  ┌────────────┴────────────┐
            ┌─────▼──────┐          ┌───────▼───────┐
            │ PostgreSQL │          │  Image store  │
            │  16 + ext  │          │  (disk+webp)  │
            └────────────┘          └───────────────┘
```

Three ideas carry most of the design:

- **Shared contracts.** Request and response shapes are defined once as Zod
  schemas in `@museumos/contracts`, imported by the API and both frontends. The
  type contract can't drift.
- **Flexible schema.** Core exhibit fields are real columns; category-specific
  fields live in JSONB, validated against a JSON Schema stored on the category
  row. Adding a field to "Computers" is a data change, not a migration.
- **Auditable by default.** Every mutation is recorded, and deletes are soft
  (`deleted_at`). Nothing a volunteer does is unrecoverable.

## Tech stack

| Layer | Technology |
|------|------------|
| **Language** | TypeScript (strict), Node.js 22+ |
| **Monorepo** | pnpm workspaces |
| **Backend** | NestJS 11, Prisma 6 |
| **Database** | PostgreSQL 16 (`uuid-ossp`, `unaccent`, `pg_trgm`) |
| **Frontend** | React 19, Vite 6, Tailwind CSS, shadcn/ui |
| **Validation** | Zod (shared `@museumos/contracts`) |
| **Auth** | Postgres-backed sessions (`express-session` + `connect-pg-simple`), Argon2id, Helmet |
| **Images** | Local filesystem + `sharp` thumbnails, served statically |
| **i18n** | i18next (Greek, English, French) |

> The dev `docker-compose.yml` also starts Redis and MinIO, left over from the
> original scaffold. The application does **not** use them — images live on
> disk and there is no job queue. You can safely start only `postgres`.

## Configuration

Copy `.env.example` to `.env`. The variables the app reads:

| Variable | Required | Description |
|----------|:--------:|-------------|
| `DATABASE_URL` | ✅ | PostgreSQL connection string |
| `SESSION_SECRET` | ✅ prod | Signs session cookies. Min 32 chars; the API refuses to boot in production without it. Generate with `openssl rand -hex 64` |
| `CORS_ORIGINS` | ✅ | Comma-separated allowed origins |
| `API_PORT` | – | API port (default `3000`) |
| `NODE_ENV` | – | `development` / `production` |
| `TRUST_PROXY_HOPS` | – | Proxies that append to `X-Forwarded-For` (default `2`, matching Traefik → nginx → api). Resolves the real client IP for rate limiting and the audit log — see [DEPLOY.md](DEPLOY.md#2-reverse-proxy), the value must be exact |
| `SESSION_COOKIE_SECURE` | – | Set `false` only when terminating TLS upstream over plain HTTP |
| `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` | – | First-run administrator. Password is generated and printed once if omitted |
| `WEB_BASE_URL` | – | Public base URL of the admin app |
| `WIKIDATA_CONTACT` | – | Contact URL or email sent in the Wikidata User-Agent |
| `VITE_ORG_SHORT_NAME` | – | Your museum's short name, used in generated social captions |
| `VITE_PUBLIC_SITE_URL` | – | Public site that exhibit permalinks point at |
| `VITE_SOCIAL_HANDLE` / `VITE_SOCIAL_HASHTAGS` | – | Defaults for the marketing composer |
| `EBAY_CLIENT_ID` / `EBAY_CLIENT_SECRET` / `EBAY_MARKETPLACE` / `EBAY_ENV` | – | Optional "Find on eBay" integration |
| `META_APP_ID` / `META_APP_SECRET` / `META_OAUTH_REDIRECT_URI` | – | Optional marketing integration |

For production, start from [`.env.production.example`](.env.production.example).

## Data model

The heart of the schema is a single `exhibits` table:

- **Typed core columns** shared by everything — display ID, name, category,
  manufacturer, year, donor, location, condition, validation and publish flags,
  timestamps.
- **A JSONB `attributes` column** for category-specific fields, validated
  against the JSON Schema stored on each row of `categories`.

Supporting tables: `categories`, `donors` (+ `donor_files`), `locations`,
`tags`, `exhibit_images`, `exhibit_notes` (the conservation log), `users`,
`role_permissions`, `audit_log`, `http_sessions`.

The seed ships 16 categories aimed at a computing collection — *Books, Cards,
Computers, Consoles, Devices, Magazines, Motherboards, Others, Parts,
Peripherals, Power Supply, Processors, RAMs, Software, Storage, Terminals*.

## Adapting it to your collection

Categories are data, not code. To make MuseumOS fit a different collection:

1. **Edit the categories** in [`packages/db/prisma/seed.ts`](packages/db/prisma/seed.ts)
   before your first seed. Each entry has a code, bilingual names, an ID prefix
   (the `PC` in `PC00544`), and a JSON Schema describing its fields.
2. **Or change them from the UI** afterwards — Settings → Categories has a field
   editor that adds, renames and reorders fields, and manages dropdown values,
   without touching the database directly.
3. **Set your locations** in the same seed file, or add them under Locations.
4. **Add your language** by dropping a JSON file into
   `apps/web/src/i18n/locales/` and `apps/pwa/src/i18n/locales/`.

Adding a field to an existing category never requires a migration.

## Security

- **Authentication** — server-side sessions stored in PostgreSQL
  (`connect-pg-simple`), HTTP-only cookies, `SameSite=Lax`, `Secure` in
  production. Passwords hashed with **Argon2id**. The session is regenerated on
  login to prevent fixation.
- **Authorization** — deny-by-default: a global guard rejects any request
  without a session, and a second guard enforces a verb + resource permission
  (`exhibit:write`, `donor:read`) declared per endpoint. Roles map to an
  admin-editable permission matrix.
- **Rate limiting** — a global throttle, plus a much tighter bucket on
  `/auth/login` (10 attempts per 15 minutes per IP) to blunt credential
  stuffing. This keys on `req.ip`, so `TRUST_PROXY_HOPS` must exactly match
  your proxy depth — otherwise every client shares one bucket, or clients can
  spoof their address.
- **Hardening** — Helmet headers, Zod validation on every request body, soft
  deletes, and an audit-log entry for every mutation.

Two things to know before you expose an instance:

- **`/img` is served without authentication.** Uploaded images and donor
  documents are reachable by anyone who knows the URL. If you store scanned
  donation forms containing personal data, put that path behind your proxy's
  auth.
- **There are no CSRF tokens.** State-changing requests rely on `SameSite=Lax`
  cookies, which covers the common cases but is weaker than token-based
  defence. Worth adding if you run this on a shared domain.

Found a vulnerability? Please open a private security advisory rather than a
public issue.

## Languages & themes

- **Trilingual** — Greek, English and French, all strings via i18next. Search is
  accent-insensitive, so Greek queries match regardless of diacritics.
- **Four themes** via CSS custom properties: `light`, `dark` (OLED black),
  `museum` (parchment + brass), and `modern`.

## Deployment

The production stack is plain Docker Compose
([`docker-compose.prod.yml`](docker-compose.prod.yml)): PostgreSQL, a nightly
backup job, the API (which runs `prisma migrate deploy` on boot), and nginx for
the admin app and the PWA — behind whatever reverse proxy you already run.

It fits comfortably on a Raspberry Pi 5 or a small VPS.

Full instructions, including a pre-flight security checklist, are in
**[DEPLOY.md](DEPLOY.md)**.

## Contributing

Issues and pull requests are welcome — especially from other museums adapting
this to their own collections.

- Use [Conventional Commits](https://www.conventionalcommits.org/) (`feat:`,
  `fix:`, `chore:` …).
- TypeScript strict mode everywhere; keep UI strings in i18n, never hardcoded.
- Run `pnpm typecheck` before opening a PR — it must pass clean.

**Good first contributions**

- **Wire up ESLint.** [`eslint.config.mjs`](eslint.config.mjs) exists and the
  `lint` scripts are defined, but the toolchain was never added to the
  workspace, so `pnpm lint` doesn't run. Installing it and clearing the
  resulting findings would be a genuinely useful first PR.
- **Add tests.** There is no test suite yet. The search and permission layers
  are the highest-value places to start.
- **Add a language.** Drop a JSON file into the two `locales/` directories.
